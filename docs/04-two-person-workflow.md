# 04. 双人分工、Git 协作与交付节奏

## 基础分工（可经两人协商调换）

**A — 架构、后端、集成与发布**

- 项目初始化、API 契约、后端工具目录与校验。
- 企业登录接入、部署包构建、Azure 配置、日志及回滚（须经 IT 授权）。
- 真实工具接入测试和跨模块联调。

**B — 前端、页面、交互与体验**

- React 初始化、统一 Shell（侧栏/顶栏/路由）、七页结构。
- 首页和工具导航优先：卡片、筛选、搜索、收藏、状态、空态和错误态。
- 按统一设计规范实现并验收 UI。

**共同：** API 契约、PR 评审、测试、安全审查、版本说明、交接文档。

## Git 规范

- `main` 为可发布分支，遵守已有保护策略。
- 一事一分支：`feat/portal-shell`, `feat/tool-api`, `fix/spa-refresh`。
- 开发完成：本地测试 → Push → Pull Request → 同伴 Review → 合并。
- 只允许一个责任人修改共享配置的某一项；接口变更先更新 docs/api-contract.md。
- PR 描述：变更范围、原因、测试命令、截图（仅可公开演示内容）、风险和回滚方法。
- 重要发布创建 tag，例如 `v0.1.0-internal`；保存发布 ZIP 与 Git SHA（留在批准的存储中）。

## AI 编程的边界

- 将任务限于指定目录；不要让多个 AI 会话同时修改同一公共组件。
- 让 AI 先列计划、修改范围、验证方式，再执行。
- 不允许 AI 自行修改 Azure 权限、分支保护、企业安全配置或直接上传公司资料。
- 每个功能完成后运行对应测试，记录实际结果而非“应该可以”。

## 15 分钟同步

1. 已合并什么 PR？
2. 今天要交付的**一个**可测试结果是什么？
3. 哪个接口或文件可能冲突？
4. 哪项权限/部署阻塞需要处理？

## 最小团队协作成果

- 双方各自成功 Clone。
- 双方各提交一个小 PR，并互相完成 Review。
- API 契约中的工具目录字段一致。
- 能从 main 构建一致的 ZIP 并在测试环境发布。
